# Cold Email AI Agent Build Checklist

**Before any cold email agent goes live**

From Ty Shane · OpenClaw Insider · 10x Cold Leads

Use this before you connect a sending inbox, before the first live send, and again after any major change to leads, copy, or handoff rules.

Drawn from the AI Agent Blueprint: start with the recurring job as it already exists, gather the four inputs, test against work the business trusts, then keep a human in the loop where judgment matters.

---

## 1. Recurring job definition

Start here. Do not invent the agent and invent the process at the same time.

- [ ] Write the job in one sentence: what recurring outbound work this agent owns
- [ ] Ask (or document for yourself): "Show me how you already do it"
- [ ] Capture the current path in plain language (lead source → first touch → reply handling → booking → sales handoff)
- [ ] Note who owns each step today (person, tool, or both)
- [ ] Collect examples of finished work the team already trusts (good emails, good replies, good booking notes)
- [ ] List the exceptions the team barely notices anymore (those usually hold the quality bar)

**Pass when:** someone who does the job can read your one-pager and say "yes, that is the work."

---

## 2. Four inputs (operating knowledge)

Collect these before you touch tools. Sharing an SOP gives context. It does not make every output correct.

### Source
- [ ] Where do leads / contacts come from?
- [ ] What fields are required before a contact can enter a sequence?
- [ ] What is excluded on purpose (competitors, existing clients, unsubscribed, wrong ICP)?

### Checks
- [ ] What does the team verify before a first send?
- [ ] What do they verify before a follow-up?
- [ ] What signals mean "pause" or "escalate to a human"?

### Finished work
- [ ] What should a finished first email contain?
- [ ] What should a finished reply contain (and what should it never invent)?
- [ ] What should a booking handoff contain for sales?

### When something looks wrong
- [ ] Wrong company / wrong person: stop and flag
- [ ] Unclear or emotional reply: human review before send
- [ ] Booking conflict or no-show path: who owns recovery?
- [ ] Tool failure (CRM, calendar, sending platform): fail closed, alert a person

**Pass when:** each of the four inputs has at least one concrete example attached.

---

## 3. Cold email workflow map

Map the agent to the business process, not to a feature list.

| Stage | What the agent may do | Human required? |
| --- | --- | --- |
| Leads | Pull or score candidates against ICP rules | Define rules; review sample |
| Write | Draft first touch and follow-ups from approved facts | Approve voice guide + sample set |
| Replies | Classify and draft responses | Approve sensitive / sales-intent replies |
| Book | Offer times / create holds per calendar rules | Confirm booking policy |
| Sales handoff | Summarize context into CRM / Slack / email | Confirm destination + fields |

- [ ] Leads stage scoped and sample-checked
- [ ] Write stage limited to approved facts and offers (no invented claims)
- [ ] Replies stage has classification labels (interested, not now, OOO, unsubscribe, angry, wrong person)
- [ ] Book stage uses real calendar availability and clear confirmation language
- [ ] Sales handoff includes contact, thread summary, next step, and source campaign

**Pass when:** you can point at input → result → how you checked it for each stage.

---

## 4. Testable success checks (before go-live)

Start with a task small enough to describe and a result clear enough to check.

Run a dry run on a fixed sample (for example 10-20 contacts the team already knows).

- [ ] Right contacts selected (ICP match rate on the sample)
- [ ] Right exclusion rules applied (no known clients / unsubscribes in the sample)
- [ ] Drafts use approved facts only (product, offer, proof, CTA)
- [ ] Tone matches the voice guide (humanizer / style rules applied after facts)
- [ ] Links and booking URL correct
- [ ] Reply drafts do not invent pricing, guarantees, or availability
- [ ] Booking path creates the correct event / hold
- [ ] Sales handoff fields complete and readable
- [ ] Side-by-side review with a trusted human sample: useful, not just "sounds good"

**Pass when:** every failed check has a named fix, not a vague rebuild.

---

## 5. Human handoff and approval rules

Do not let the agent send into a network without clear gates.

- [ ] First-send approval: human signs off on the sequence before live
- [ ] Reply approval: which reply classes auto-draft only vs need send approval
- [ ] Escalation list: anger, legal, press, VIP, refund, competitor
- [ ] Logging: every send and reply classification stored with timestamp and contact id
- [ ] Kill switch: who can pause the agent, and how fast
- [ ] Daily / weekly review owner named

**Default safe posture:** draft-only until the sample set passes. Expand autonomy only after checks stay green.

---

## 6. Do not ship

Stop. Fix these before any live inbox is connected.

- [ ] No clear recurring job definition
- [ ] Four inputs incomplete or only guessed
- [ ] No trusted finished examples to compare against
- [ ] Invented offers, metrics, or testimonials in copy
- [ ] No unsubscribe / suppression handling
- [ ] No human approval path for sensitive replies
- [ ] No sales handoff destination
- [ ] No kill switch or logging
- [ ] Sending platform warm-up / domain posture unreviewed by the operator
- [ ] Agent allowed to expand to "run the whole company" before one stage works
